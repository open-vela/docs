# Adapting an I2C Bit-Banging Driver

[ English | [简体中文](../../../../../zh-cn/device_dev_guide/driver/bus_driver/I2C/i2c_bitbang_guide.md) ]

Bit-banging is a technique that uses general-purpose input/output (GPIO) pins to simulate the I2C protocol timing. This method is useful when a chip has an insufficient number of hardware I2C controllers or when a non-standard pin combination is required.

> **Performance Warning**: Bit-banging relies entirely on the CPU to control GPIO levels through software loops. To ensure precise timing, it is often necessary to **disable interrupts** in critical code paths. This increases system interrupt latency and can impact real-time performance. Therefore, you should always prioritize using a hardware I2C controller when one is available.

## I. Adapting the Lower Half Interface

The lower-half adaptation for bit-banging is very simple; it only requires implementing a set of GPIO operation functions.

### 1. Kconfig Configuration Options

```Makefile
CONFIG_I2C=y
CONFIG_I2C_BITBANG=y 
```

### 2. Implementation Steps

The core of the adaptation is to provide an instance of the `struct i2c_bitbang_lower_ops_s` structure and call `i2c_bitbang_initialize()` to "glue" it to the upper-half generic driver.

- Reference implementation: [cxd56_i2cdev_bitbang.c](https://github.com/apache/nuttx/blob/master/boards/arm/cxd56xx/common/src/cxd56_i2cdev_bitbang.c)

#### Step 1: Implement the GPIO Operation Function Set

The developer needs to provide an instance of the `struct i2c_bitbang_lower_ops_s` structure, which contains the low-level GPIO operation functions.

<details>
<summary>Click to expand code</summary>

```C
struct i2c_bitbang_lower_ops_s
{
  /* Initialize pins to appropriate state (usually open-drain) */

  CODE void (*initialize)(FAR struct i2c_bitbang_lower_dev_s *lower);

  /* Set high/low level for SCL/SDA pins */

  CODE void (*set_scl)(FAR struct i2c_bitbang_lower_dev_s *lower, bool high);
  CODE void (*set_sda)(FAR struct i2c_bitbang_lower_dev_s *lower, bool high);

  /* Read level of SCL/SDA pins */

  CODE bool (*get_scl)(FAR struct i2c_bitbang_lower_dev_s *lower);
  CODE bool (*get_sda)(FAR struct i2c_bitbang_lower_dev_s *lower);
};
```

</details>

#### Step 2: Implement the Initialization Function

In the board-level code, populate the `i2c_bitbang_lower_dev_s` structure, and then call `i2c_bitbang_initialize()` to get a standard `i2c_master_s` handle.

<details>
<summary>Click to expand code</summary>

```C
static const struct i2c_ops_s g_i2c_ops =
{
  i2c_bitbang_transfer  /* transfer */
#ifdef CONFIG_I2C_RESET
  , NULL                /* reset */
#endif
};

struct i2c_bitbang_lower_dev_s
{
  FAR const struct i2c_bitbang_lower_ops_s *ops;
  FAR void *priv;
};

FAR struct i2c_master_s *i2c_bitbang_initialize(
    FAR struct i2c_bitbang_lower_dev_s *lower)
 {
      dev->i2c.ops = &g_i2c_ops;
      dev->lower = lower;
      dev->lower->ops->initialize(dev->lower);

      return &dev->i2c;
 }
```

</details>

## II. Upper-Half Application Layer Usage

The `i2c_master_s` handle generated by the bit-bang driver is **fully compatible** with the handle from a hardware Master driver. You can:

1. **Use Directly in Kernel Drivers**: After obtaining the `i2c_master_s` handle in the board-level initialization code, pass it directly to other kernel drivers that require it (such as sensor drivers). This is the most common use case.
2. **Register as a User-Space Device**: Call the `i2c_register()` function to register the handle as a `/dev/i2c-N` device node. This allows user-space programs to access it via `ioctl`, which is very useful for debugging with command-line tools like `i2ctool`.
