# Boot Process

## I. Board-Level Initialization Sequence

The openvela board-level initialization process is as follows:

```C
nx_start->
    board_early_initialize->
           // Start AppBringup_task CONFIG_BOARD_INITTHREAD_STACKSIZE
           board_late_initialize->
                   // Start nsh_task CONFIG_INIT_STACKSIZE
                   board_app_initialize->
                       rc.sysinit->
                           board_app_finalinitialize->
                                   rcS->
```

1. `nx_start`: The entry point of the openvela OS.
2. `board_early_initialize`: This is used for early board initialization, dependent on CONFIG_BOARD_EARLY_INITIALIZE. The execution context is the idle task, and no events can be waited upon, nor can any blocking functions (such as sem_wait, as the basic components of the OS have not yet been initialized) be called. 
3. `board_late_initialize`: This is executed later than board_early_initialize and is the entry point for the initialization of most board-level drivers. The OS basic components are already ready at this point, and the execution context is a temporary AppBringup thread of the kernel, where events can be waited for. Most chip driver initializations occur in this step. 
4. `board_app_initialize`: Used for application initialization, called via boardctl(BOARDIOC_INIT). The execution context is the nsh task. Note that the file system cannot be accessed at this stage. 
5. `rc.sysinit`: The boot script of openvela is divided into two stages. The current one is the first stage script, mainly used for file system mounting and core service initialization, executed before the nsh input prompt. 
6. `board_app_finalinitialize`: Used for final board initialization, boardctl(BOARDIOC_FINALINIT). The execution context is the nsh task. Drivers that need file system access (such as TP, Charger, Audio PA, BMI, PPG, and GPS) should be moved to this phase and can directly operate files without using delay work to defer execution. 
7. `rcS`: The second-stage script, primarily used to start other applications, including miwear, algo_service, gpsd, and healthd. It is executed before the nsh input prompt.

## II. Boot Scripts

The startup scripts `rcS` and `rc.sysinit` of openvela are loaded and parsed by the `nsh task` through `nshlib`, and the location of the startup scripts is specified by the `config`:

1. `CONFIG_ETC_ROMFSMOUNTPT/CONFIG_NSH_SYSINITSCRIPT`
2. `CONFIG_ETC_ROMFSMOUNTPT/CONFIG_NSH_INITSCRIPT`

The startup scripts are typically placed under `/etc`, and the `etc` directory contents are linked to the openvela binary in the form of `romfs`. After booting, it is automatically mounted by the kernel, and the relevant configuration is as follows:

```Makefile
CONFIG_FS_ROMFS=y
CONFIG_ETC_ROMFS=y
CONFIG_ETC_ROMFSMOUNTPT="/etc"
CONFIG_NSH_SYSINITSCRIPT="init.d/rc.sysinit"
CONFIG_NSH_INITSCRIPT="init.d/rcS"
```

The openvela etc is generated by different boards. The `genromfs` and `xxd` tools can be used to generate `etc_romfs.c`, which is compiled into the kernel.

For example: `boards/arm/at32/at32f437-mini/src/etc_romfs.c` is generated by the script `boards/arm/at32/at32f437-mini/tool/mkromfs.sh`.

A more commonly used method is to generate the `etc` content from the corresponding `board/arch/board/board/src/etc` directory.
For example: `boards/sim/sim/sim/src/etc`.

All content under `etc` is controlled by the Makefile of the parent directory of `etc/`, where `RCSRCS` is used to specify startup scripts, and `RCRAWS` is used to specify other files and directories to be included in the `etc` directory.

```Makefile
ifeq ($(CONFIG_ETC_ROMFS),y)
  RCSRCS = etc/init.d/rc.sysinit etc/init.d/rcS
  RCRAWS = etc/group etc/passwd
endif
```
